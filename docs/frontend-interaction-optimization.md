> 更新日期：2026-05-16  
> 文档定位：下一阶段前端体验路线图  
> 分析基础：项目代码审查 + 交互设计讨论

---

## 一、文档边界

这份文档关注的是：**在不改变核心产品边界的前提下，让当前前端体验更连续、更清楚、更一致。**

因此它优先处理：

- 用户已经投入内容后的控制权与保护
- 关键路径中的理解成本与操作效率
- 跨页面的一致性、品牌感与移动端可用性

以下内容不再与主路线图混排，而是单列为“产品扩展项”：

- 全文搜索
- 日程到期提醒通知
- AI 报告导出/分享
- Markdown 实时预览
- 首次使用引导（Onboarding）
- 系统主题跟随

这些能力都值得评估，但它们会扩展产品范围、牵涉新的决策或后端配合，不应挤占当前体验修整的优先级。

## 三、路线图主题

### 1. 保护用户投入

这是第一优先级。目标不是“增加功能”，而是避免用户在已经投入时间后丢失内容或失去控制权。

#### 1.1 会话过期处理

- **现状**：`useApi` 检测到 401 后只调用 `logout()`，无提示、无显式跳转
- **问题**：用户会突然失去上下文，不知道自己为什么回到未登录状态
- **建议**
  - 会话过期后跳转登录页
  - 使用 Toast 明确提示“会话已过期，请重新登录”
  - 需要区分主动退出与被动失效
- **涉及文件**：`hooks/useApi.ts`、`contexts/AuthContext.tsx`

#### 1.2 AI 长任务连续性

把原“停止生成”和“断线保护”合并为一个专题处理，避免状态散落。

- **现状**
  - 已有流式渲染
  - 已有 `AbortController`
  - 但缺少用户可见的停止入口，以及中断后的明确状态表达
- **目标**
  1. 生成中可主动停止
  2. 停止后保留当前已生成内容，并明确标记为“未完整”
  3. 区分手动停止、断网、超时、服务端失败等结束方式
  4. 明确“恢复边界”后，再决定采用本地草稿恢复还是服务端状态恢复
- **注意**
  - 不应直接默认“实时写入 `localStorage`”
  - AI 内容可能包含隐私文本，恢复策略先是产品与隐私决策，再是实现细节
- **涉及文件**：`pages/AI/ChatView.tsx`

#### 1.3 自动保存草稿

- **现状**：关闭页面会丢失日记/日程编辑内容
- **建议**
  - 对日程与日记编辑提供草稿自动保存
  - 重新进入时提示并允许恢复
  - 成功保存后清除草稿
- **涉及文件**：`pages/Schedule/Schedule.tsx`、`pages/Thoughts/Thoughts.tsx`

#### 1.4 未保存离开保护

- **现状**：取消编辑或切换离开时，未保存修改可能直接消失
- **建议**
  - 检测脏状态
  - 在取消编辑、切页或关闭前给予确认
  - 与自动保存草稿配合，避免形成两套互相打架的提示机制
- **涉及文件**：`pages/Schedule/Schedule.tsx`、`pages/Thoughts/Thoughts.tsx`

#### 完成定义

- 用户已输入的内容不会无提示丢失
- AI 生成过程可被用户主动中断
- 用户能够看懂一次中断后的结果是否完整、是否还能继续
- 主动退出、会话失效、页面刷新三类场景不会混淆

### 2. 可理解性与操作效率

这部分解决“用户知道发生了什么、下一步该做什么、常用操作是否顺手”。

#### 2.1 空状态、错误态、加载态统一

- **现状**
  - 历史页等页面仍存在纯文字空状态
  - 各页面的空状态、错误反馈、加载反馈表达方式并不统一
- **建议**
  - 统一复用 `EmptyState`
  - 补足关键空状态下的下一步动作
  - 形成一致的 loading / error / retry 表达
- **涉及文件**：`pages/History/History.tsx`、相关页面与共享组件

#### 2.2 表单实时验证

- **现状**：多数校验集中在提交时，且较多依赖 Toast
- **建议**
  - 对高频表单增加内联验证
  - 把“格式错误”与“提交失败”分开表达
  - 减少用户在点击提交后才发现问题

#### 2.3 日历“回到今天”

- **现状**：用户切到其他月份后，没有快捷返回当前日期的方式
- **建议**：在日历头部加入“今天”操作，返回当前月并选中今天
- **涉及文件**：`pages/History/History.tsx`

#### 2.4 图表数据点跳转

- **现状**：分析图表能看趋势，但不能直接回到对应记录
- **建议**：点击数据点跳到相应日期的历史记录页
- **涉及文件**：`pages/Analysis/Analysis.tsx`、`pages/Analysis/MoodTrendChart.tsx`

#### 2.5 批量操作键盘多选

- **现状**：批量选择依赖逐个点击
- **建议**
  - 支持 `Shift` 连续多选
  - 支持 `Ctrl`/`Cmd` 不连续多选
  - 让批量模式更接近常见桌面操作模型

#### 2.6 全局键盘快捷键

- **建议**
  - `Ctrl+N` 新建日程
  - `Ctrl+K` 聚焦后续搜索入口
  - `Esc` 关闭弹窗或退出次级状态
- **注意**：快捷键应避开输入区冲突，并与可见菜单提示一致

#### 完成定义

- 关键页面的空状态都能回答“现在能做什么”
- 常见错误能在输入阶段被看见，而不是提交后才暴露
- 用户可以更快地在“趋势”和“记录”之间往返
- 高频桌面操作不再完全依赖鼠标逐点点击

### 3. 交互视觉一致性

这部分先定义系统规则，再落到具体组件。  
最近 Analysis 页的调整已经说明：问题常常不在某个组件“设计不好”，而在它没有接入全站一致的视觉语义。

#### 3.1 先建立跨页面规范

至少需要统一：

1. 按钮层级
2. 卡片与边界强度
3. 空状态、错误态、加载态表达
4. 选中态反馈
5. 动效时长、缓动与进入/退出规则
6. `reduced-motion` 降级策略
7. 浅色/暗夜模式下的等价表现

#### 3.2 组件级落地项

- 情绪调谐器的微交互升级
- 按钮模式、滑块模式、调谐器模式的选中态统一
- 页面切换动效
- 其他能强化 Seven Sense 气质、但不破坏克制感的局部微交互

#### 完成定义

- 同类控件在不同页面呈现相同的视觉语义
- 浅色与暗夜模式都遵循同一套系统逻辑
- 页面转场和局部反馈有一致节奏，不互相抢戏
- 关闭动画后，页面信息结构仍然完整

---

### 4. 移动端核心路径适配

移动端问题不应被简化成“把 Sidebar 改掉”。  
真正需要保证的是，用户能在手机上顺畅完成核心路径。

#### 4.1 必须覆盖的场景

1. 登录后的主导航
2. 日程录入表单
3. 日记编辑
4. AI 对话输入区与软键盘
5. 历史页日历与详情
6. 分析页图表与长报告阅读
7. 弹窗、浮动操作栏与底部安全区

#### 4.2 当前已知问题

- Sidebar 在移动端仍以桌面侧栏思路存在
- 页面主体的表单密度、图表阅读、软键盘遮挡与固定操作区风险仍需专项检查

#### 建议方向

- 导航层面评估底部 Tab 与抽屉式导航的取舍
- 对核心路径逐页做小屏重排，而不是只做媒体查询收缩
- 明确移动端不依赖 hover、不过度要求横向滚动

#### 完成定义

- 用户可在手机上完成“添加记录 -> 写日记 -> 查看分析”主流程
- 关键操作不会被软键盘、固定栏或安全区遮挡
- 高频页面无需依赖 hover，且尽量避免横向滚动

## 四、建议实施顺序

### 第一阶段：保护用户投入

1. 会话过期处理
2. AI 长任务连续性
3. 自动保存草稿
4. 未保存离开保护

### 第二阶段：提升可理解性与操作效率

5. 空状态、错误态、加载态统一
6. 表单实时验证
7. 日历“回到今天”
8. 图表数据点跳转
9. 批量操作键盘多选
10. 全局键盘快捷键

### 第三阶段：建立系统一致性

11. 交互视觉一致性规范
12. 情绪输入组件统一
13. 调谐器与局部微交互升级
14. 页面切换动效

### 第四阶段：完成移动端核心路径适配

15. 导航模式调整
16. 日程、日记、AI、历史、分析页面的小屏适配
17. 弹窗、固定栏、输入区与安全区治理

## 五、产品扩展项

这些建议值得保留，但不属于当前体验路线图的主线。

| 项目 | 说明 |
|------|------|
| 全文搜索 | 需要后端接口与信息架构支持 |
| 日程到期提醒通知 | 涉及权限策略、浏览器能力与可能的服务端配合 |
| AI 报告导出/分享 | 属于新增传播能力 |
| Markdown 实时预览 | 会改变写作模型，不只是输入体验优化 |
| 首次使用引导 | 更接近激活策略，需要单独设计 |
| 系统主题跟随 | 属于主题策略扩展 |

## 六、暂不建议直接投入的事项

### 列表虚拟化

- 当前还缺少明确的性能证据
- 在项目约束下，不应为了“可能会慢”就提前引入额外复杂度或依赖
- 建议在出现可复现的大列表性能问题后，再单独评估

---

## 七、后续需要先做决策的开放项

1. **AI 恢复边界**  
   是只恢复本地未提交草稿，还是恢复服务端未完成生成状态？

2. **移动端导航方案**  
   更适合底部 Tab，还是抽屉式导航？

3. **键盘快捷键范围**  
   只覆盖桌面高频路径，还是要建立全局快捷键体系？

4. **视觉规范落地方式**  
   是先写一份 design token / component rule 文档，还是直接在共享样式层中收敛？

---

## 八、验收视角

完成这条路线图后，至少应能观察到这些变化：

- 用户在中断、刷新、误操作后更少丢失内容
- 高成本任务（如 AI 生成、长文本编辑）有更明确的控制感
- 新用户面对空页面时更容易知道下一步
- 不同页面之间的视觉语言更统一
- 手机端不再只是“能打开”，而是能完成完整核心流程
